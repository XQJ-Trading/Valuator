# Phase 5 — 비교 마일스톤

전체 아키텍처: [overview.md](overview.md). 선행: Phase 1-4 완료.

## 목표

E(PageIndex) 운영이 안정화된 뒤 청크 필터링(현행 베이스라인) 및 벡터 RAG와 정성·정량 비교를 통해 시나리오별 라우팅 정책을 결정한다.

## 비교 대상

### A. 현행 청크 필터링

- 위치: [`sec_tool.py`](../../valuator/tools/sec_tool.py)의 `_extract_chunks` 기반 흐름
- 비교 비용: 0 (기존 코드 그대로)
- 의미: E의 도입 정당성 사후 검증. 결과에 따라 일부 시나리오는 청크 필터링으로 되돌릴 수도 있음.

### B. 벡터 RAG (pgvector + 임베딩)

- 위치: 신규 구축 필요 (인프라 도입 비용 발생)
- 시점: 코퍼스 확장 시점에 평가 — 여러 회사·여러 연도 한꺼번에 검색하는 시나리오가 실제로 생긴 뒤
- 검토 방향: E 단독 vs 벡터로 후보 문서 선별 + E 트리 탐색의 하이브리드

## A 비교 절차

1. 질의 셋 준비
   - 기존 `session_store`에서 실제 사용자 질의 회수 (10-20개)
   - 단순 추출형, 구조적 질의형, 교차참조형으로 분류
2. 동일 질의로 청크 필터링·트리 추론 두 경로 실행
3. 비교 지표
   - 응답 정확도 (수동 평가, rubric 기반 1-5점)
   - 인용 페이지 정확도 (수동 확인)
   - 토큰 비용 (검색 단계만)
   - wall-clock 시간
4. 결과로 시나리오별 라우팅 정책 결정
   - 예: 단순 추출은 청크, 구조적/교차참조 질의는 E

## B 비교 절차

1. 트리거: 사용자 시나리오가 "여러 회사·여러 연도 동시 검색"으로 확장된 시점
2. pgvector + 임베딩 인프라 PoC 구축
3. E 단독 vs (B로 후보 5-10편 선별) + (각 편마다 E 트리 탐색) 두 경로 비교
4. 비교 지표
   - 응답 정확도
   - 검색 후보 선별의 recall (B가 정답 문서를 누락하지 않는가)
   - 인프라 도입 비용 (개발 + 운영)
5. 결과: B 단독 도입 / 하이브리드 / B 미도입 중 선택

## 산출 지표

- A 대비 E의 응답 정확도 차이 (질의 유형별)
- A 대비 E의 인용 정확도 차이
- A 대비 E의 검색 단계 토큰 비용 비율
- 시나리오별 라우팅 정책 (구체적 분류 기준)
- B 도입 정당성 평가 결과 (정량 임계값, 예: "코퍼스 N편 이상 + recall 손실 < X% 일 때 도입")
